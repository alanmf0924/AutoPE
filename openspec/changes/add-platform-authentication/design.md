# Design

## Context

参见 [proposal.md](proposal.md)。现有 `security.py` 使用本地全角色旁路或自实现 HS256；`main.py` 已在多数端点放置 `require_roles`，但身份来源、资源范围和自审关系未闭合。前端仅启动时查询一次 `/api/session`。第一版产品必须独立安装，不以现有 OA 的接口能力、企业 IdP、邮箱或外部网络为前提。

## Goals / Non-Goals

**Goals:**

- 落实 [platform-identity](specs/platform-identity/spec.md)、[platform-authorization](specs/platform-authorization/spec.md) 与 [operator-audit](specs/operator-audit/spec.md)。
- 允许一台初期服务器同机运行同源入口/前端、API、独立 Worker 与 PostgreSQL，并由主机挂载 Secret 提供既有外部 Secret 解析要求；这是单机多服务部署，不是单进程或高可用承诺。
- 初始化、登录、管理账号、评测与独立审批均不需要 OA/SSO；身份或审批证据不可确认时失败关闭，前端给出恢复路径。

**Non-Goals:**

- 员工/部门/流程管理、公开自助注册、邮箱依赖、第一版 OIDC/JWKS/企业组同步、改造现有 OA、为 Worker 伪造人员身份、自动修改生产 Dify。

## Decisions

1. **第一版选择内置账号；企业 SSO 后置。** 账号持有独立稳定 ID、规范化唯一登录名、状态和密码哈希；密码使用成熟密码哈希组件的 Argon2id，不存明文或可逆密文。未来身份来源可通过内部主体抽象扩展，但本次不开发 OIDC 网关、JWKS 验证或组映射。直接复用 OA Cookie/数据库会让开源安装依赖另一系统，故不采用。
2. **安装初始化与恢复由服务器控制。** 空账号库时，具备服务器/容器管理权限的部署者经交互式 CLI 生成短期一次性初始化凭据；浏览器同源 HTTPS 的设置页消费它并创建唯一初始管理员。令牌仅显示一次、服务端存摘要、事务中核验空库并消费；初始化后入口关闭。平台管理员可创建账号并生成一次性邀请/重置凭据交给用户，无 SMTP 前置条件；自身锁死时由服务器权限控制的 CLI 发起审计化恢复。备选默认 admin 密码、开放注册均不采用。
3. **同源不透明会话替代浏览器 Bearer。** API 验证服务端保存的会话摘要及账号当前状态/角色；浏览器只持有 `HttpOnly`、生产 `Secure`、适当 `SameSite` 的会话 Cookie。会话设置空闲与绝对超时；登出、停用、密码重置立即撤销。状态不可读时拒绝写入。写请求使用与会话绑定的 CSRF 证明并校验来源；登录/设置入口也检查来源。生产仅经 TLS 同源入口访问 API，入口剥离客户端操作者/角色头。仅显式本机隔离开发档位可用 HTTP 与测试便利配置，共享测试/生产不能开启全角色旁路。备选 SPA 存储 Access Token 不采用。
4. **平台管理员与业务角色分离。** `platform_admin` 仅可管理账号和业务角色，不自动授予 `approver`。初始管理员获得平台管理权限和 `operator`，可创建其他账号与分配五类业务角色；服务端每次按账号最新状态和角色授权，默认空业务权限。前端按 `/api/session` 允许动作展示入口，但 API 是裁决者。角色更改、重置和停用留下审计。即使管理员赋予自己 `approver`，自审与硬门禁依然不可绕过。
5. **独立审批按主体与证据版本判断。** 为测试集当前版本、候选创建/绑定、标注及交接保存已核验贡献主体；批准时在同一事务内重读角色、对象版本/摘要和贡献人集合。测试集详情与报告审核视图向客户端提供当前 SHA-256 证据摘要，测试集批准、发布决定、人工交接创建和回填须用 `If-Match` 提交所见摘要；已核验模式下缺少前置条件返回 428、摘要变化返回 412，均不产生批准或交接。`If-Match` 仅防止旧视图提交，不能替代服务端重算摘要、角色和贡献人。当前版本贡献人不能批准相应对象；只有一个管理员时可完成准备和评测，但其本人证据必须等另一名合格审批人加入才能批准。仅比较 `created_by` 会漏掉后续编辑，因此不采用。
   - **贡献关系按当前版本追踪。** 测试集同一版本的创建、上传、冻结及重新签署主体均计入；不能因正文摘要变化而丢掉创建人的冲突关系。候选创建、生成、绑定及人工绑定证明的人员，以及报告当前标注/重开人员须由服务端已核验会话写入可信记录；Worker、旧 `reviewer_id` 文本及客户端自填字段不能冒充人员。发布决定检查当前测试集、候选绑定及本次报告标注的可信贡献人，并阻止其中任何人自审；人工交接创建和回填重检决定当前性及同一冲突集合。
   - **旧对象显式重签，不追认历史。** 旧测试集由具备 `operator` 角色的已核验人员在当前摘要上重新签署；旧候选使用现有绑定证明路径由 `prompt_owner` 重签当前绑定；旧标注由获分配的 `annotator` 重新提交当前证据。每次签署仅证明此刻版本已被该人员复核，保留旧记录原貌，并使签署人成为该版本贡献人，须由另一名 `approver` 批准。无法重新确认的历史对象仅可读取，不能产生新批准。开发/测试显式本地全角色旁路只用于旧演示流程，不作为可信贡献或上线验收。
6. **审计来源明确，不追认旧身份。** 新写入、账号管理和关键拒绝记录请求 ID、稳定账号 ID、当时角色、`local_verified`、结果与对象版本；无有效主体的 401 只记匿名安全事件。旧 `actor_id` 原样保留并标 `local_unverified`，不自动映射到新账号。凭据和敏感正文不入审计；审计查询按角色与对象范围遮蔽。
7. **会话恢复不自动重放写入。** 页面内存保留未提交草稿；401 后重新登录、重取证据与权限、用户再确认。403 展示权限问题不重试。幂等键防网络重试重复写入，但不能将旧审批自动重放。

## Control-plane and Safety Boundaries

`operator` 管目标、测试集与评测；`annotator` 处理分配证据；`prompt_owner` 准备候选；`approver` 处理独立审批与人工交接；`auditor` 只读。现有允许 `annotator` 建集/冻结、`operator` 标注的接口将按新矩阵收紧，属于兼容性变更。候选生成和评测仍需原有的显式外部传输授权；登录不等于数据外传授权。高风险/红线硬门禁、待复核及运行时错误独立于角色与总分。平台仅记录 Dify 人工控制台交接，不自动发布或回滚生产版本。

## Data, Migration, and Compatibility

- 用 Alembic 增量迁移新增本地账号、角色授予、会话摘要、一次性凭据摘要、审计来源/结果、可信贡献人及对象分配关系；存储使用 PostgreSQL，生产部署不以 SQLite 验收。迁移前备份并在隔离库做恢复演练；密码和令牌明文不得入库。
- 迁移前审计保留原文本并标 `local_unverified`；历史对象缺可信贡献人时只读展示“需重新签署/复核”，不自动算作双人审批。既有报告和决定可读，新增批准走新规则；新增可信贡献记录不回填旧 `actor_id`。
- `/api/session` 增加账号、角色、允许动作和会话状态；新增初始化、登录、登出、密码与账号管理操作。旧浏览器构建与新后端不应混用；先迁移与部署兼容读取，再同时切入口/API/前端。旧自签 HS256 和全角色旁路在共享测试/生产失效，旧客户端收到 401/403。
- 明确区分本机隔离测试、共享测试和生产；任何可被其他人员访问的环境都强制真实鉴权和 TLS。生产保留既有外部 Secret 解析要求，允许由部署者控制的主机挂载 Secret 提供，不强制企业 Secret SaaS。
- 回退优先停止新增写入、回退兼容应用版本并保留新列、新账号与审计；不得清除已写证据或以打开全角色旁路回滚。若旧版无法安全读取新状态，则只读维护并修复向前版本；恢复 PostgreSQL 前由责任人批准并核对备份点。

## External Calls and Human Authorization

- 本地登录、会话、账号管理和初始化不调用 OA/IdP/邮箱；第一版的身份链路无外部网络调用，故无身份服务调用预算。使用本地限速、超时与最小日志；不因网络失败降级为全角色旁路。
- 本鉴权变更不新增 Dify 或模型调用。自动测试使用隔离账号与桩运行时；任何真实评测/候选生成、模型输入、Dify 调用或数据外传都需另行确定数据范围、目标、调用次数/费用预算、超时和显式授权，不作为默认鉴权验收。
- 生产凭据注入、初始管理员交付、角色矩阵、共享测试与生产流量切换、备份恢复由部署/业务负责人批准。Dify 发布与回滚始终由人员在 Dify 控制台完成并回填证据。

## Risks / Trade-offs

- [单机部署是单点] → 明确备份、监控与 Worker 任务恢复；若有高可用目标再拆分数据库和应用实例，单机联调不等于 HA。
- [服务器权限可触发管理员恢复] → 限制主机/容器访问、一次性限时凭据、交互式操作和可读回审计；恢复责任人由部署方指定。
- [管理员可为自己分配角色] → 保留角色变更审计，所有批准仍检查不同主体、证据版本和硬门禁；生产角色矩阵由业务负责人确认。
- [历史贡献人不可信] → 历史证据只读保留，真实身份重新签署后方可新批准；不做虚假回填。
- [前端草稿包含敏感内容] → 只在当前页面内存暂存，会话恢复后重新校验；刷新或关闭页面不承诺跨会话持久恢复。

## Verification Plan

- 本地确定性测试：空库/并发/重复初始化、错误凭据与限速、密码重置、会话过期/撤销、CSRF、全端点权限矩阵、资源分配、自审与证据变化、审计脱敏、迁移兼容。使用隔离 PostgreSQL 和桩运行时，不调用真实 Dify/模型。
- 浏览器测试：初始化、登录/登出、管理员建人赋权、五类角色视图、受限 URL/API、401 草稿恢复、403 提示、权限变化后重新提交、CSRF 拒绝；静态构建或截图不代替真实操作证据。
- 自托管共享测试真实运行时：在无 OA/IdP/邮箱的安装中记录初始化、双账号登录、Cookie/CSRF、直接 API 越权、停用与会话撤销、独立审批、审计读回、备份恢复和 Worker 状态；仅用获批准的测试数据。
- 人工发布门禁：业务负责人签署角色/兼职/冲突矩阵，部署方确认域名/TLS、初始管理员、Secret、备份与回退；未完成时状态保持“待联调/待批准”。
