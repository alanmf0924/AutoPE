# Spec Delta

## Purpose

为 AutoPE 的账号管理、数据集、标注、候选、评测与人工发布交接提供服务端角色和对象授权，使开源独立部署也能管人管权，且兼职账号不能绕过独立审批与既有安全门禁。

## ADDED Requirements

### Requirement: 平台管理员管理本地账号和角色
系统 SHALL 将账号创建、停用、重置与业务角色分配限制为已核验的平台管理员；平台管理员是一项账号管理权限，不自动取得业务批准权，也不得覆盖独立审批规则。默认不开启公开注册。

#### Scenario: 管理员创建和停用账号
- **WHEN** 平台管理员创建本地账号、分配业务角色或停用账号
- **THEN** 系统保存变更并使后续请求按最新账号状态与权限执行

#### Scenario: 普通用户或匿名者改权
- **WHEN** 非平台管理员直接请求创建账号、修改角色或重置他人密码
- **THEN** 系统返回 401 或 403，且不改变账号、角色或会话状态

#### Scenario: 管理员尝试业务批准
- **WHEN** 仅有平台管理员权限的账号请求批准测试集或发布决定
- **THEN** 系统返回 403；即使同时有 `approver`，仍须通过对象冲突与硬门禁检查

### Requirement: 业务角色只来自服务端账号授权
系统 SHALL 根据服务端保存的账号授权授予 `annotator`、`operator`、`prompt_owner`、`approver`、`auditor`；无业务角色的已登录账号默认无业务权限，多个角色不能绕过对象级冲突规则。

#### Scenario: 多角色人员
- **WHEN** 一个已核验账号获授多个业务角色
- **THEN** 系统仅授予这些角色对应的操作，并继续执行独立审批约束

#### Scenario: 未授权或伪造角色
- **WHEN** 已登录人员缺少操作所需角色，或请求体/请求头自填 `approver`
- **THEN** 受限业务操作返回 403，且不改变资源或审批状态

### Requirement: 每项业务操作在 API 执行权限检查
系统 SHALL 在服务端按操作和对象范围检查权限；`operator` 管理目标、测试集与评测，`annotator` 处理获分配的复核证据，`prompt_owner` 管理候选与绑定，`approver` 执行批准及发布交接，`auditor` 仅只读审计范围内的证据。导航和按钮状态不得替代 API 授权。

#### Scenario: 直接调用越权写接口
- **WHEN** `auditor` 绕过前端按钮直接请求创建评测、修改标注或批准发布
- **THEN** API 返回 403，且不触发模型/Dify 调用或业务状态变化

#### Scenario: 标注员访问非分配证据
- **WHEN** `annotator` 请求未分配给自己的标注对象
- **THEN** 系统拒绝读取或写入该对象，且响应不泄露受限正文

#### Scenario: 前端权限变化
- **WHEN** 当前账号的业务角色发生变化
- **THEN** 前端刷新允许动作与导航；即使旧页面仍可见，服务端仍按最新权限拒绝越权提交

### Requirement: 审批人不能批准本人准备的证据
系统 SHALL 在测试集批准、报告/候选发布决定和 Dify 人工交接前重新检查当前角色、对象版本与操作者关系；审批人与该对象的创建、修改、标注或候选准备主体冲突时 SHALL 拒绝，即使该账号同时具备多个角色或平台管理员权限。

已核验部署模式下，系统 SHALL 向审批视图提供服务端计算的当前证据摘要，并要求测试集批准、发布决定、人工交接创建及回填使用 `If-Match` 提交所见摘要；缺少前置条件或摘要不匹配时 SHALL 拒绝写入。客户端摘要不得成为贡献主体或可信证据的来源。

#### Scenario: 测试集自审
- **WHEN** 创建或修改当前测试集版本的人员使用 `approver` 角色批准该版本
- **THEN** 系统返回 403，测试集保持未批准状态并留下不含敏感正文的拒绝审计

#### Scenario: 候选或标注自审
- **WHEN** 候选负责人或本次报告所依据标注的提交人批准该候选的发布决定
- **THEN** 系统返回 403，发布决定不会创建

#### Scenario: 审批期间证据改变
- **WHEN** 审批人看到的报告摘要、测试集版本或候选绑定在提交前发生变化
- **THEN** 系统拒绝旧版本审批并要求重新查看当前证据

#### Scenario: 缺少所见证据摘要
- **WHEN** 已核验审批人未提交 `If-Match` 就请求测试集批准、发布决定或人工交接
- **THEN** 系统返回 428 且不产生批准或交接；提交的摘要与服务端当前值不一致时返回 412

#### Scenario: 旧对象重新签署
- **WHEN** 历史测试集、候选绑定或标注缺少已核验的当前版本贡献人
- **THEN** 系统不得直接新增批准；已核验的 `operator` 可签署当前测试集版本，`prompt_owner` 可重新证明当前候选绑定，获分配的 `annotator` 可重新提交当前标注，之后仅其他 `approver` 可批准，旧操作者文本和旧证据保持原样

#### Scenario: 单管理员首次安装
- **WHEN** 系统只有初始管理员且该人准备了需独立审批的证据
- **THEN** 该人可以继续准备和评测，但不能批准自己的证据；须新增另一名合格审批人

### Requirement: 人工发布边界与硬门禁不可由角色覆盖
`approver` 身份 SHALL 只允许在当前且完整的 GO 证据基础上批准平台发布决定和记录 Dify 人工控制台交接；角色授权不得覆盖高风险/红线失败、未复核或执行错误，也不得自动调用生产 Dify 发布或回滚。

#### Scenario: 高风险失败仍有高总分
- **WHEN** 比较报告总分达标，但高风险或红线用例失败
- **THEN** 即使请求者是 `approver` 或平台管理员，系统仍拒绝 GO 批准与发布交接

#### Scenario: 未复核或运行时错误
- **WHEN** 报告仍有待人工复核用例或 Dify 运行时调用错误
- **THEN** 系统拒绝批准发布，不把该状态当作质量通过

#### Scenario: 批准后交接
- **WHEN** 独立审批人提交有效发布决定
- **THEN** 平台仅创建可追溯的人工交接记录，不自动修改生产 Dify Prompt、发布或回滚版本
