# Dify Runtime 接入与生产化实施计划

## 目标

将 Dify_AutoPE 从“可登记 Dify 目标、创建排队任务”升级为独立、可审计的评测执行平台：Worker 使用被测 Dify 应用的后端 API 执行冻结测试集，生成可复核的结果、报告和人工标注队列。平台不写入或发布 Dify Prompt。

## 边界

- 仅调用用户配置的 Dify App API；密钥仅存于服务端凭据存储，API 与页面绝不回显。
- 普通、高风险、红线门禁分别为 85%、100%、100%；安全维度不允许被自动“放宽”。
- 不能从一段自然语言期望中可靠判定“是否调用了正确工具”。没有机器可判定断言的用例会进入人工复核，而不会伪造自动分数。
- 本地 Dify 可以在开发环境使用本地加密凭据；生产环境只允许 PostgreSQL、已启用鉴权和外部密钥解析器。

## 本次实施

1. 为评测任务增加租约、尝试次数、错误摘要、Worker 心跳和逐用例执行结果。
2. 实现独立 Worker：原子认领排队或过期租约任务，按用例执行基线/候选 Dify 目标，失败可恢复；逐用例结果唯一，避免重试重复计数。
3. 以显式机器断言计算自动评分；无断言、调用失败或安全风险一律生成待人工标注项。自动评分只作为门禁依据与复核建议。
4. 汇总四维评分、风险分层通过率、P95 延迟和失败用例，生成报告；Worker 存活情况纳入就绪检查。
5. 补齐迁移、单元/集成测试、运行手册和生产前置检查。

## 验收

- 创建任务后，Worker 能将任务从 `queued` 转为 `running` 再到 `completed` 或 `failed`。
- Worker 崩溃留下的过期租约可被另一 Worker 接手；同一用例不会被重复写入最终结果。
- Dify 错误、超时、无可判定断言和门禁失败均可追溯到用例与报告，并进入人工队列。
- 本地自动化测试、静态检查、迁移演练和前端构建通过。

## 上线前仍需人工完成

- 填写本机 Dify App API Key，并用非敏感的真实工作流做一次端到端运行。
- 配置 PostgreSQL、外部密钥管理、JWT/OIDC、反向代理 HTTPS、备份与日志留存策略。
- 在双 Worker 的 PostgreSQL 环境完成租约抢占、进程中断恢复、Dify 超时与限流演练后，再决定生产发布。
